
# Аналіз Spotify Tracks за допомогою MongoDB

## Опис проєкту

Проєкт демонструє роботу з MongoDB Atlas на основі набору даних Spotify Tracks Dataset.

Проєкт включає:
- Завантаження даних CSV у MongoDB.
- Трансформацію необроблених документів за допомогою MongoDB Aggregation Pipeline.
- Виконання аналітичних запитів.
- Створення індексів для підвищення продуктивності запитів.

## Використані технології

- Python 3.13
- MongoDB Atlas
- MongoDB Shell (mongosh)
- PyMongo 4.7.3
- Pandas
- JavaScript (MongoDB Aggregation Pipeline)

## Структура бази даних

База даних: `spotify`

Колекції:

- `tracks_raw` — необроблені дані, імпортовані з CSV.
- `tracks` — трансформовані дані з вкладеними аудіохарактеристиками та додатковими полями.

## Трансформація даних

Конвеєр агрегації виконує такі операції:

- Перетворює рядок виконавців на масив.
- Групує аудіохарактеристики в об'єкт `audio_features`.
- Обчислює тривалість треку в секундах.
- Присвоює рівні популярності: high, medium, low.

## Аналітичні запити

Проєкт містить чотири запити:

1. Пошук треків, придатних для вечірок.
2. Визначення популярних виконавців.
3. Виявлення аномальних значень темпу за жанрами.
4. Пошук інструментальних фонових треків.

## Встановлення та запуск

Встановлення залежностей:

```bash
py -m pip install -r requirements.txt
```

Налаштування підключення до MongoDB Atlas у файлі `.env`:

```text
MONGO_URI=your_mongodb_connection_string
```

Перевірка підключення:

```bash
py test_connection.py
```

Завантаження CSV:

```bash
py scripts/01_load_data.py
```

Трансформація даних:

```bash
mongosh "YOUR_MONGO_URI" --file scripts/02_transform.js
```

Запуск аналітичних запитів:

```bash
mongosh "YOUR_MONGO_URI" --file queries/part2_queries.js
```

Створення індексів:

```bash
mongosh "YOUR_MONGO_URI" --file scripts/03_create_indexes.js
```

Порівняння складених індексів:

```bash
mongosh "YOUR_MONGO_URI" --file queries/part3_indexes.js
```

## Індексація та продуктивність запитів

В експерименті порівнюються три складені індекси для запиту з такими умовами:

- `track_genre: "pop"`
- `audio_features.danceability >= 0.7`
- Сортування за `popularity` у спадному порядку.

### Порівняння продуктивності

| Індекс | Перевірено документів | Перевірено ключів | Час виконання | Етап SORT |
|---|---:|---:|---:|---|
| Жанр + популярність | 1 000 | 1 000 | 2 мс | Ні |
| Жанр + danceability + популярність | 354 | 354 | 1 мс | Так |
| Жанр + популярність + danceability | 354 | 412 | 1 мс | Ні |

Усі три індекси повернули однакові 354 документи.

### Аналіз результатів

**Індекс 1 — Жанр + популярність**

- Перевіряє 1 000 документів.
- Фільтрація за danceability виконується після сканування індексу.
- Не потребує окремого етапу SORT.

**Індекс 2 — Жанр + danceability + популярність**

- Перевіряє лише 354 документи та 354 ключі індексу.
- Забезпечує ефективну фільтрацію за danceability.
- Потребує додаткового етапу SORT.

**Індекс 3 — Жанр + популярність + danceability**

- Перевіряє 354 документи та 412 ключів індексу.
- Забезпечує сортування за популярністю без окремого етапу SORT.
- Забезпечує компроміс між фільтрацією та сортуванням.

Для цього запиту третій індекс є вдалим компромісом, оскільки підтримує потрібний порядок сортування та зменшує кількість документів, які потрібно перевірити.

Час виконання дуже малий і може змінюватися між запусками. Тому різницю між 1 мс і 2 мс не слід вважати остаточним доказом переваги.

Для порівняння використовувалися `explain("executionStats")` та `hint()`, які дозволяють явно перевірити кожен індекс.

Реалізація експерименту знаходиться у файлі `queries/part3_indexes.js`.

### Індекс для інструментальних фонових треків

Створено складений індекс за полями:

- `audio_features.instrumentalness`
- `audio_features.speechiness`
- `explicit`

Запит використовує умови:
- instrumentalness > 0.5
- speechiness < 0.1
- explicit = false

Результати виконання:

| Показник | Результат |
|---|---:|
| Знайдено документів | 16 141 |
| Перевірено документів | 16 141 |
| Перевірено ключів індексу | 16 844 |
| Час виконання | 50 мс |

План виконання використовує IXSCAN із подальшим FETCH. Це підтверджує використання складеного індексу замість повного сканування колекції.

### Covered Query (Запит, покритий індексом)

Для перевірки Covered Query використано складений індекс:

```javascript
{ track_genre: 1, popularity: -1 }
```

Запит повертає лише поля, які містяться в індексі:

```javascript
db.tracks.find(
    { track_genre: "pop" },
    { _id: 0, track_genre: 1, popularity: 1 }
)
```

**Результати виконання:**

| Показник | Результат |
|---|---:|
| Час виконання | 0 мс |
| Повернуто документів | 1 000 |
| Перевірено документів | 0 |
| Перевірено ключів індексу | 1 000 |

MongoDB використала етапи `PROJECTION_COVERED` та `IXSCAN`. Етап `FETCH` не знадобився.

Це підтверджує, що запит повністю виконується за допомогою індексу без звернення до документів колекції.
